# 05. 音声解析連動 Q&A

実施日: 2026-05-12

---

## Q1: 音声解析（FFT/ビート/音量/ピッチ等の特徴量抽出）はどこで、いつ実行される想定ですか？

**選択肢**: 1) UTAVISTA内蔵・読込時一括 / 2) リアルタイム解析 / 3) 外部ツール事前解析 / 4) 外部AI

**回答**: 1. UTAVISTA 内蔵、音声ファイル読み込み時に一括解析・キャッシュ。

→ 帰結:
- 既存 v0.5.1 の BeatDetector/AudioAnalyzer 資産を統合・拡充して活用
- 解析結果は **時系列の特徴量データ** として確定保存（決定論性確保）
- 再生・シーク・エクスポートで毎回再計算しない

---

## Q2: 抽出して保存しておきたい「音声特徴量の種類」は？

**選択肢**: 1) 標準セット一括 / 2) 標準 + ユーザー追加可 / 3) オンデマンド / 4) FFT生のみ

**回答**: 2. 標準セット + ユーザー追加可（カスタム帯域、特殊解析）。

→ 帰結:
- 標準セット: `volume`, `lowBand`, `midBand`, `highBand`, `beat`, `pitch` 等
- UI から追加設定可能: 「800Hz 帯の音量」「ボーカル帯域のオンセット」等のカスタム
- 各特徴量は名前付きで管理 → テンプレ側からは `audio.<featureName>(t)` で参照
- 追加された場合は再解析が走る

---

## Q3: テンプレ（もしくはトラック）のパラメータと「音声特徴量」をどうマッピングさせたいですか？

**選択肢**: 1) IR内直接記述 / 2) 別UIで配線 / 3) ハイブリッド / 4) AI主導

**回答**: 3. ハイブリッド（単純 mapping は UI、複雑式は IR 記述）。

→ 帰結:
- **単純なリンクは UI で**: Inspector に「このパラメータに音声マッピング」UI。レンジ・スケール・オフセット・反転・スムージングを設定
- **複雑な式は IR で直接**: 複数特徴量の組み合わせ・条件分岐・カスタム計算は IR Atom 直記述（手動 or AI）
- マッピング設定はパラメータ側に保持: `parameter.modulationSource = { feature, mapping: {...} }`

---

## Q4: 「音声特徴量をマッピングできるパラメータ」の範囲は？

**選択肢**: 1) 数値型は全テンプレで可 / 2) テンプレ作者が明示宣言したものだけ / 3) 既定セット限定 / 4) 既定可+作者がオプトアウト

**回答**: 2. テンプレ作者が「このパラメータはマッピング可」と明示宣言したものだけ。

→ 帰結:
- IR `ParameterSpec` に `audioMappable: boolean` を追加
- UI: `audioMappable: true` のパラメータのみ「音声マッピング設定」UI を表示
- AI 生成テンプレも同フィールドを宣言する
- 安全志向（予期せぬパラメータへの接続を防ぐ）

---

## Q5: 解析した「音声特徴量データ」はどこに保存したいですか？

**選択肢**: 1) .uta に同梱 / 2) サイドカーキャッシュ / 3) アプリ共通キャッシュ / 4) 都度再解析

**回答**: 1. .uta プロジェクトファイルに同梱。

→ 帰結:
- プロジェクトの自己完結性優先。別 PC に移しても再解析不要
- ファイルサイズは増えるが、データ圧縮（DCT/差分エンコード等）で抑制可能
- 音声ファイルが変わったら再解析が必要

## サマリー（このテーマで明確になったこと）

1. **解析実行**: UTAVISTA 内蔵、ファイル読み込み時に一括（既存 BeatDetector/AudioAnalyzer 資産を統合）
2. **特徴量**: 標準セット（音量・低中高帯域・ビート・ピッチ） + ユーザー追加可
3. **マッピング**: ハイブリッド（単純UI / 複雑式IR）
4. **適用対象**: テンプレ作者が `audioMappable` で明示宣言したパラメータ
5. **保存**: .uta に同梱

### 新たな IR 設計要件

- **AudioFeature ドメイン Atom IR**: `audio.featureName(t) → number` の純関数として参照可能
- **ParameterSpec 拡張**: `audioMappable: boolean` フィールド
- **ModulationSource 構造**: `{ feature, mapping: { range, scale, offset, smoothing, reverse } }`
- **データ層**: `.uta` 内に `audioAnalysis: { features: { [name]: TimeSeries }, customConfigs: [...] }`

### データモデル（増分）

```
Project {
  ...既存...
  audioAnalysis: AudioAnalysisData
}

AudioAnalysisData {
  audioFileHash: string  // 整合性確認用
  sampleRate: number     // 解析サンプリング率（例: 30Hz）
  features: { [name: string]: TimeSeries<number> }
  customConfigs: CustomFeatureConfig[]
}

ParameterSpec {
  ...既存...
  audioMappable?: boolean
}

ParameterValue {  // 各パラメータの実際の値
  baseValue: any
  modulationSource?: {
    feature: string  // 'kick', 'volume', etc.
    mapping: {
      range?: [number, number]
      scale?: number
      offset?: number
      reverse?: boolean
      smoothing?: number  // 急変緩和（ローパスフィルタ）
    }
  }
}
```

## Q6（追加質問）: タイムラインへのビート視覚化とスナップ対象は？

**ユーザーから追加要件**:
> 音声解析結果の用途として、ビート／リズムのタイミングをタイムライン上に表示し、マーカーをスナップできるようにしたい

**選択肢**: 1) ビート / 2) +小節頭 / 3) +ユーザー手動グリッド / 4) +歌詞境界

**回答（重要な深堀あり）**:
> 基本1ですが、実際の曲のスピードは必ずしも一定ではないので、**主拍を解析して適応的にスナップポイントが自動設定** されることが理想です。**ブレイクビーツ的なビートの場合にも過密スナップ点にならないような工夫** があることが理想です。

→ 帰結（音楽情報処理として高度な要件）:
- **ローカルBPM 追跡**（テンポゆらぎに追従）
- **主拍 vs 装飾拍の分離**（ハイハット連打など細かい拍を主拍と区別）
- **スナップ密度の自動調整**（人間が使いやすい粒度に間引く）
- データ層: `AudioAnalysis.beats` に加えて `mainBeats`（主拍抜粋）/`localBPM`（時系列）を保存
- UI 層: タイムラインに視覚マーカー表示、ドラッグ時の「スナップ」効果
- 既存 v0.5.1 の BeatDetector では恐らく不十分。より高度なアルゴリズム（aubio/librosa 系の DP beat tracking 等）の検討が必要

## 残された曖昧さ・追加で確認したい点

- **マッピングの粒度**: 1パラメータに複数特徴量をブレンド可能にするか
- **スムージング既定値**: 急激な変化（ノイズ的）の緩和をデフォルトでどの程度かけるか
- **解析の精度・速度バランス**: 短い曲なら一瞬、長い曲は時間かかる。プログレス UI 必要
- **解析失敗時の挙動**: 無音区間、複雑な音響、低品質音源など
- **マッピング UI が複雑化したときの整理**: 多くのパラメータに音声接続している曲で見通しが悪くならないか
- **シェーダーへの音声特徴量入力経路**（テーマ6で扱う）: シェーダー uniform も同じマッピング機構で接続
- **スナップ詳細**: ON/OFF・粒度切替の操作モデル（グローバル/クリップ別/一時無効化キー等）
- **主拍解析の実装**: 既存資産では足りない可能性、ライブラリ選定や独自実装の判断
