# UTAVISTA: ゴール駆動の再設計検討プラン

## Context（なぜこのドキュメントを書くか）

UTAVISTAは「自然言語→AIによるテンプレート生成」を新方式として導入することを目指している。だがその前に、これまでの議論で次が明確になった:

1. 既存プリミティブは"真のIR原子"ではなく、複合体（≒ミニテンプレート）が混じっている。
2. 扱う対象は **Graphic / Motion / Effect / Particle / Layout / Mask** の6ドメインに広がる。
3. アプリのビューワー要件として **任意の再生位置 t に対して画面状態が決定論的に確定** する必要がある（生成/廃棄イベント駆動ではなく純関数モデル）。
4. UIから調整したパラメータを **.uta に保存・再現**、テンプレ側から **UI公開メタデータを宣言**、**ユーザーライブラリへ永続化** できる必要がある。
5. 現状の UI/画面レイアウト・フォントリスト・テンプレート管理は「とりあえず実装」状態で挙動に不自然な点がある。これらは新方式では **完全新規設計** の対象。
6. 本プロジェクトは開発段階で、**既存ユーザーへのデータ互換性配慮は不要**。`.uta` フォーマットや既存テンプレIDも自由に変更してよい。
7. 既存バージョンの中で「対症療法的に対応してきた泥臭い知見」（スプライトタイルからのはみ出し、エフェクトのパディング、フォントメトリクス…）は、新方式でも **十分把握した上で再対応** する必要がある（再発させてはいけない）。

本ドキュメントは **実装プランではなく**、上記をふまえてゴールを詳細化し、現状資産と突き合わせて **「どこまで再設計するのが妥当か」を判断するための材料** を整理する。実装計画は方針確定後に別途作成する。

## 1. 到達したいゴールイメージ

### 1.1 ユーザー体験のシナリオ

**シナリオA — 一般エンドユーザー（歌詞アニメ作成者）**
- 想定の中心は **既存テンプレベースの差分指示**:
  1. ライブラリから既存テンプレ（例: WordSlideText 系）を選んで適用
  2. UI でパラメータを調整して概形を整える
  3. 「もうちょっと弾けるように」「光る感じを足したい」「サビは強調したい」など、**現在のテンプレに対する追加効果・変更要望を自然言語で入力**
  4. AI が「現テンプレ + 差分IR」を生成して提案 → プレビューで採用判断 → 採用すれば派生テンプレとしてライブラリに保存
- ゼロから完全新規生成は基本的にスコープ外（シナリオBへ）

**シナリオB — 上級ユーザー／テンプレート開発者**
1. ゼロから自然言語でテンプレを生成する用途もここに含まれる（「サビ最初の文字だけ大きく回転して飛び込む。後ろは薄く流れる」など）
2. ライブラリ上のテンプレを GUI エディタで読み込み、Atom/Composite IR を差し替えて派生テンプレを作成
3. 手書きで複雑なテンプレを書きたい時は、Atom/Composite IR をプログラム的に呼び出して書ける
4. 妥当性（決定論性・パラメータ公開・階層整合・スプライト余白）はビルド時／登録時に検証され、違反は明示的にエラー化される

**シナリオC — AI（外部 Claude Code 等）**
1. 入力には2系統:
   - (i) **差分生成モード**: 既存テンプレ IR + 自然言語の「変更要望」→ 差分 IR を生成（シナリオA用）
   - (ii) **新規生成モード**: 自然言語のみ → 完全な IR を生成（シナリオB用）
2. UTAVISTA にロードすると **動的に IAnimationTemplate 化** され即動作
3. 失敗時はパラメータ不整合／階層構造誤り／余白不足などが機械的に報告される
4. 決定論性は **エンジン側で構造的に保証** されるため AI 側で気にする必要はない（Atom IR の純関数契約と評価モデルが副作用を物理的に排除）

### 1.2 体験を支える品質要件（不変条件）

- **t→state 決定論はエンジン側責務**: 任意 `nowMs` で画面状態が一意に決まる。これは **テンプレ／IR 側が宣言する性質ではなく、エンジンが評価モデルとして物理的に強制する**:
  - Atom IR の関数シグネチャは「副作用無し・seed 注入で乱数化・`t` 入力で `state` 出力」を **型で強制**
  - シーク・逆再生・ジャンプ・エクスポートで同一の評価経路を通す
  - 結果として、テンプレ実装者も AI も「決定論性を意識する必要が無い」
- **3階層モデル維持**: Phrase / Word / Char。各階層は独立IRコンテキスト。
- **UI公開パラメータの宣言**: テンプレ側で `exposeToUI` メタデータ宣言。UIは自動生成。
- **.uta 永続化**: 後述の **パラメータオーバーライドモデル**（§1.7）に従って3階層／オーバーライドの差分のみを保存。フォーマットは新規設計（互換不要）。
- **エフェクトはスクリーンスペース**: 重ポストプロセス（Glow/Blur/CA等）は `app.stage` 一括。階層別個別フィルタは原則禁止。
- **ロックステップエクスポート**: プレビューとエクスポート一致（WebCodecs+FFmpeg mux）。
- **スプライト余白の宣言と上書き可能性**:
  - フォントはみ出し量＋エフェクトpadding量に基づき、**エンジン／IR が必要余白の既定値を自動算出**してテクスチャ領域を確保
  - 一方で、**UI からパラメータとして余白を上書き可能** にする（不足時の救済、過剰確保時のメモリ節約、特殊フォントへの手動対応）
  - 既定値は IR/Allocator が提示、最終値は「自動算出 + UIオーバーライド」のマージ結果

### 1.3 理想レイヤー構成

```
[Input経路]
  自然言語      ─→ [AI/Claude Code]            ─→ IR(JSON)
  GUIエディタ   ─→ [IRエディタ]                 ─→ IR(JSON)
  手書きTS      ─→ [Atom/Composite API直叩き]   ─→ IAnimationTemplate

[ライブラリ階層]
  ・ビルトイン Template (アプリ内蔵、新規実装)
  ・ユーザーライブラリ (ユーザーローカル保存)
  ・プロジェクト埋め込み (.uta内、配布用)

[ランタイム]
  IR Loader / Validator (決定論性・余白・パラメータ整合をチェック)
       ↓
  IR Compiler  →  IAnimationTemplate (動的生成)
       ↓
  Engine ── render*Container(t, start, end, phase, ctx) ──→
       ↓
  IR Atoms (純関数)
   ├ Graphic : applyAlpha, applyTint, applyScale, applyRotation, applyPosition, textStyle
   ├ Motion  : lerpXY, bezierPath, easing, phaseProgress
   ├ Layout  : charLayoutCumulative, Grid, Vertical, MultiLine
   ├ Mask    : applyRectMask, applyShapeMask, applyAnimatedMask
   ├ Effect  : screenFilterStack (Glow/Blur/Vignette/CA/Flash...)
   └ Particle: seededRandom, emitOnMotion, particleLife
       ↓
  Sprite Allocator (フォント実測 + エフェクトpadding を加味して必要余白を計算)
       ↓
  PIXI Renderer (WebGL)
       ↓
  [出力] プレビュー (Ticker駆動) / エクスポート (CFR+WebCodecs+FFmpeg mux)
```

### 1.4 理想データモデル

- **歌詞**: `PhraseUnit[] { id, text, start, end, words: WordUnit[] }` 等を新規型として確定
- **テンプレートIR**:
  ```
  TemplateIR {
    id, name, version, author?,
    parameters: ParameterSpec[],
    paddingDefaults: PaddingSpec,    // 自動算出の既定余白（UIから上書き可）
    hierarchy: { phrase: IRNode, word: IRNode, char: IRNode }
  }
  IRNode = Composite | AtomCall | Sequence | ConditionalByPhase
  ParameterSpec { name, type, defaultValue, exposeToUI, uiLabel?, uiGroup?, uiOrder?, min?, max?, step?, options?, description? }
  ```
  - 決定論性宣言フィールドは持たない。Atom IR の型契約と評価モデル側で構造的に保証。
- **プロジェクト .uta（新規フォーマット、旧形式の互換不要）**:
  - `lyrics: PhraseUnit[]`
  - `audio: AudioRef`
  - `backgroundVideo?: VideoRef`
  - `templateAssignments`: 階層別アサインメント。後述の **パラメータオーバーライドモデル**（§1.7）に従いツリー構造。
  - `parameterOverrides`: 階層ノードごとに「上書きされたパラメータ差分のみ」を保存（差分主義）。
  - `embeddedTemplates?: TemplateIR[]`（配布用、ユーザーライブラリ参照と二択）
  - `stage`: 解像度・アスペクト等のステージ設定
  - `version`: フォーマットバージョン

### 1.5 理想UI／画面レイアウト

現状の UI は「とりあえず実装」状態で、改善ではなく **完全新規設計** が前提。理想形を以下に提案する（詳細は方針確定後の別ドキュメントで詰める）。

**主要パネル構成（提案）**:

- **左カラム — ライブラリ／プロジェクト**
  - ライブラリブラウザ（ビルトイン／ユーザー／プロジェクト埋め込み を統一表示）
  - テンプレサムネイルプレビュー
  - 検索・タグ・お気に入り
- **中央上 — ステージプレビュー**
  - 16:9 などアスペクト固定の中央表示
  - スケール自動／手動切替、デバッグオーバーレイ（グリッド・フレーム情報）
  - フルスクリーン／ウィンドウ／ピン
- **中央下 — タイムラインビュー**
  - 波形＋フレーズ／単語／文字マーカー（階層をズーム連動で切替）
  - マスク／背景動画／音声を同じタイムスケール上に表示
  - **動画エクスポート範囲インジケータ**: 動画として書き出す時間区間の開始／終了を可視化（既存「選択区間を出力」機能の発展）
  - **パラメータオーバーライドインジケータ**: 個別パラメータが設定されているフレーズ／単語／文字を色や下線で示す（後述 §1.7 のオーバーライドモデルと連動）
- **右カラム — Inspector**
  - 選択コンテキスト連動（フレーズ／単語／文字／プロジェクト）
  - パラメータエディタ（テンプレIRの `exposeToUI` を自動展開）
  - グループ化・展開状態の保存
  - **継承の可視化**: 「このパラメータは親から継承」「このパラメータは自分で上書き」「上書きを破棄してデフォルトに戻す」をパラメータ単位で操作可能（§1.7 参照）
- **トップバー** — プロジェクト操作（保存/開く/エクスポート）、ビューモード切替、ツールパレット
- **モーダル／ドロワー** — AI生成ダイアログ（自然言語入力＋生成中表示＋差分プレビュー）、フォント管理、設定

**UI 設計原則**:
- 階層（Phrase/Word/Char）と「継承／上書き」を **常に視覚化** — ユーザーがどのレベルでパラメータが効いているか迷わない
- AI 生成プロセスは「指示入力／生成中／プレビュー／採用／破棄／微調整」のステートマシンを明示
- 既存テンプレへの差分指示（シナリオA）と新規生成（シナリオB）は入口を分け、差分指示時は **現在のテンプレと提案の差分プレビュー** を必ず見せる
- フォント管理は独立ウィンドウ／パネル（後述の新規設計）

### 1.6 新規設計が必要な周辺機能

**(a) フォント管理（完全新規設計）**

ユーザー指摘の現状不自然点は「実使用フォントだけをアクティベートして、パラメータUIにはアクティベートしたフォントのみを表示したいが、選択がうまく反映されないことがある」。要件はここを確実に動かすこと。ライセンス管理など他要素は不要。

- **フォント一覧のアクティベート選択 UI**: システム検出フォント全てを表示し、ユーザーがチェックでアクティベート。選択状態は永続化（プロジェクト or アプリ設定のどちらにするかは設計時決定）。
- **パラメータUIへの絞り込み反映**: テンプレパラメータの `fontFamily` 系プルダウンは、アクティベートされたフォントだけを候補に出す。選択状態と表示候補が確実に同期する設計（現状の不自然挙動の原因を解消）。
- **オプション調査**: フォントごとの **実測メトリクス**（ascent/descent/サイドベアリング）取得が技術的に可能か調査。可能ならスプライト余白計算（§1.2）に渡す経路を追加。不可能なら手動オーバーライド前提で進める。
- フォントプレビュー（簡易な試し描きでアクティベート選択を補助）も範囲に含める

**(b) テンプレート管理（完全新規設計）**

- ライブラリの3区分（ビルトイン／ユーザー／プロジェクト埋め込み）を統一インターフェースで扱う
- インポート／エクスポート（単一テンプレ・複数テンプレ・依存関係込み）
- バージョニング（同名テンプレの新旧管理）
- IR バリデーション結果の表示（余白宣言の妥当性・パラメータ整合）
- 検索・タグ・カテゴリ

### 1.7 パラメータオーバーライドモデル（個別アクティベーションの代替提案）

現状の「個別アクティベーション」は、全体にテンプレを適用した上で一部だけパラメータを差し替えるための **対症療法的実装** とユーザー認識。これを置き換える代替モデルを比較検討する。

#### 代替案A — 階層的継承モデル（CSS-like）**【推奨】**

- パラメータ値は **デフォルト値 → グローバル → Phrase → Word → Char** の順で評価し、各レベルで「明示的に上書き」されたパラメータだけ保持
- **「アクティベート」操作は不要**: ユーザーは Inspector でパラメータを変更すると、その階層レベルで自動的に上書き(override)になる
- 上書き解除も同じ Inspector で「親に戻す」アクションで自然に表現
- ツリービュー上で「このフレーズはどのパラメータを上書きしているか」を一目で可視化
- データは差分だけ保存される（`.uta` は軽量）
- **メリット**: 概念が単純、CSS と同型で学習負荷低、すべての階層に同じ規則が適用される
- **検討点**: 大量のフレーズに対して「サビ全部だけ変えたい」のような **論理的グループ単位の一括変更** がやや面倒（複数選択して一括Edit を補助）

#### 代替案B — 名前付きパラメータプリセット

- 「メインスタイル」「強調スタイル」など **名前付きパラメータセット** を定義
- フレーズ／単語／文字に「このスタイルを使う」と指定
- 階層的継承（A）と組み合わせ可能: あるスタイルを基底にして個別override
- **メリット**: 再利用性が高い、共有パターンを定義しやすい
- **検討点**: スタイル定義の管理 UI が必要、概念が一段増える

#### 代替案C — タグ／シーンベース

- ユーザーが「サビ」「Aメロ」「ブリッジ」「強調」などのタグをフレーズに付与
- パラメータを **タグ別にオーバーライド** 可能
- **メリット**: 大量のフレーズで論理的グループ管理がしやすい（A の弱点を補完）
- **検討点**: タグ定義の作業が必要、AとBの上にもう一段の抽象

#### 代替案D — タイムベース・キーフレーム

- パラメータが時間軸で変化する（例: `fontSize` が 0:30 で 32→48 にトランジション）
- **メリット**: 動的変化を表現しやすい
- **検討点**: パラメータ管理が複雑、UI 負荷大、現状のニーズに対して過剰の可能性

#### 推奨

**A（階層的継承）を基底にしつつ、C（タグ）でグループ単位の一括上書きを補助** するハイブリッド案を推奨。

- A だけで全機能カバー可能だが、「サビ全部」のような操作頻度が高いとされる用途で C が効く
- B は将来拡張として有用だが Phase 1 では必須ではない
- D は対象外（必要が出てきたら別途検討）

#### 既存「個別アクティベーション」からの違い

|軸|既存方式|推奨A+C|
|---|---|---|
|操作モデル|アクティベート ON/OFF → 値変更|値を変更すれば自動 override|
|解除|アクティベート OFF（値は保持）|親に戻す（差分削除）|
|管理単位|個別オブジェクト|階層継承＋タグ|
|.uta 保存|個別パラメータ完全保存|差分のみ|
|UI 視覚化|緑マーカー|継承ツリー＋override 表示|

### 1.8 既存実装に埋もれた「暗黙知」の体系化（最重要）

これがユーザーから今回特に強調された論点。新方式で再発させないために、**現バージョン開発で対症療法的に対応した実装を発掘して体系化する**必要がある。

**既知の例（着手前に網羅すべきものの一部）**:

- **フォントはみ出し**: 一部のフォントは行ボックス／文字ボックスの想定サイズより大きく描画される（特に装飾系フォント、ディセンダ・アクセント・カーニング外字）。スプライトタイルが切れる。
- **エフェクトのpadding**: PIXI のグロー・ボカシ・グリッチ等フィルタは描画領域より外側にも色が乗る。フィルタの `padding` 設定とテクスチャサイズ拡張が必要。
- **テクスチャアトラスサイズの上限**: WebGLテクスチャの最大寸法に当たる前にスケールダウン or 分割描画する処理。
- **高DPI対応**: CSS スケーリングと PIXI resolution の関係、[known-issues.md](docs/known-issues.md) の LINE-HEIGHT-001 の根因。
- **背景動画とテキストレイヤーの解像度／AR整合**: v0.7.0で対応した検証ログの背景。
- **GPUメモリリーク対策**: オフスクリーンRenderTextureプールの初期化／破棄、`gl.finish()`/`gl.flush()` タイミング、シーク後の背景動画フリーズ。
- **シークと再生方向**: シーク中・逆再生中の挙動。
- **音声時間オフセット**: 音楽ファイル先頭にオフセットがあるケースの整合。
- **マスクの直書き対応**: 一部テンプレ内のマスク処理ロジック。
- **個別アクティベーション解除時のパラメータ保持仕様**: グローバル設定と個別設定のマージ規則。
- **テンプレートパラメータの拡張ID対応**: parameter-management-guide v0.6.0 で追加された仕様。

**体系化のアプローチ**:

1. Phase 0 として **「現状実装の暗黙知抽出」** を独立フェーズに置く
2. ソース横断と git log 横断、`known-issues.md` 精査、コメント／関数名／コミットメッセージから「対症療法ポイント」をリスト化
3. 抽出した各ポイントを **IR 設計の入力要件（不変条件・規約・契約）に翻訳** する
4. 例: 「フォントはみ出し」→ IR の `requiredPadding` メタデータ規約に翻訳、`SpriteAllocator` 層が責務として吸収
5. 翻訳できない／IR の枠に収まらない暗黙知があれば、それは設計ギャップとして §3 に追加

このフェーズを **やらずに再設計に入ると確実に再発する** ため、ゴールに到達するための必須プロセスとして組み込む。

## 2. 現状でできていること（資産棚卸し）

### 結論案（叩き台）

**「PIXI/レンダリング基盤・WebCodecsエクスポート・GPU安定化ノウハウは流用、それ以外は新規設計」のアグレッシブな再設計**が妥当。

互換性配慮が不要になったことで、以下が変わる:
- `.uta` フォーマットを刷新可能（旧データ移行ロジック不要）
- ParameterManagerV2 や ProjectStateManager の **思想は継承するが実装は新規** にしてよい
- 既存5テンプレは新IRが安定するまでの **参考実装・検証材料** として残し、新IRで等価実装が揃った時点で完全撤去
- UI コンポーネント階層、ストア構造（Zustand 等の本格導入も含む）も白紙で設計可能

実質的には **「全面再設計に近いが、レンダリングコアと出力パイプラインだけ温存」** という構造になる。これは前回プランの Option β より Option γ 寄り。

## 5. ゴールに向けた進め方の選択肢（判断材料）

### Option α — 現状最大限活かす段階改善
- IR層は作らず、既存プリミティブのドキュメント整備とエンジン契約明文化だけで AI 連携を立ち上げる
- メリット: 短期投資少
- リスク: 暗黙契約・Composite/Atom 混在・UI不自然挙動を抱えたまま AI に乗せる → 生成失敗率高・保守困難・暗黙知再発
- 互換不要前提でこの選択肢の合理性は **更に低下**

### Option β — コア温存・IR層を新規構築
- Engine／Export／一部 Parameter を流用、IR・AI・ライブラリ・UI再設計
- メリット: 中程度コストでゴールに近づける
- リスク: UI・フォント・テンプレ管理が新規となるとコア境界の調整が結局多い

### Option γ — レンダリングコアのみ流用、それ以外を新規設計（**推奨案・更新**）
- 流用: PIXI レンダリング基盤、WebCodecs+FFmpegエクスポートパス、GPU安定化ノウハウ（暗黙知として §1.8 で抽出）
- 新規: IR層、エンジン契約、Engine の上位構造、状態管理、UI/UX、フォント管理、テンプレート管理、AI 連携、ユーザーライブラリ、.uta フォーマット、SpriteAllocator
- 既存5テンプレ・llm/・IntentBasedAPI・各 Manager 系は **参考材料として残しつつ、新規実装で置換**
- メリット: 設計の純度高く、暗黙知再発リスクを最小化
- コスト: 大（数か月オーダー）

### Option δ — 完全新規（PIXIすら別検討）
- PIXI ベースを継続するかも改めて判断（threejs / WebGPU / 純Canvas 等の選択肢を再評価）
- メリット: 純度最大、将来の拡張自由度
- コスト: 過大。エクスポートパスのv0.7.0安定化を捨てる損失が大きく **推奨しない**

## 6. ゴール確認チェックリスト（書き直し）

ゴール像の妥当性をユーザーが判断するための観点。実装完了基準ではなく **ゴール像の確認** が目的。

**体験**
- [ ] 一般ユーザー(A)は「既存テンプレベースの差分指示」が中心、新規生成(B)は上級ユーザー向け、という想定でよいか
- [ ] AI 生成テンプレを **ユーザーライブラリ** に保存し、他プロジェクトから呼び出せる仕様でよいか
- [ ] プロジェクト配布時、依存テンプレを `.uta` に同梱する選択肢を持つ仕様でよいか

**技術**
- [ ] **決定論性はエンジン側が責務として保証**（テンプレ／AI が意識する必要なし）でよいか
- [ ] IR 階層を Atom / Composite / Template の3層にする方針でよいか
- [ ] 6ドメイン（Graphic/Motion/Effect/Particle/Layout/Mask）で十分か、追加すべきドメインはあるか
- [ ] スプライト余白は **エンジン側で自動算出、UI からの上書き可能** という設計でよいか
- [ ] パーティクルも seed+規則で `t→粒子集合` 再現する方針でよいか
- [ ] **パラメータオーバーライドモデルは「階層的継承(A)+ タグ(C) ハイブリッド」**で進める方針でよいか（§1.7）

**範囲**
- [ ] UI／画面レイアウトを完全新規設計とする方針でよいか（§1.5 の構成案レビュー）
- [ ] フォント管理は「アクティベート選択の確実動作 + 実測メトリクス取得の実現性調査」に絞る方針でよいか（§1.6）
- [ ] テンプレート管理は3区分統一・バージョニング・検証結果表示中心で、適用履歴は不要（§1.6）でよいか
- [ ] 既存5テンプレ・llm/ 配下・IntentBasedAPI は参考材料として残しつつ新規実装で置換、でよいか
- [ ] PIXI レンダリングコアと WebCodecs+FFmpegエクスポートだけ流用する Option γ でよいか

**プロセス**
- [ ] 設計着手の前に **Phase 0「暗黙知抽出」** を必須フェーズとして置く方針でよいか
- [ ] GUI テンプレートエディタは IR 完成後の後フェーズで構わないか

## 7. このドキュメントで決定したいこと

1. **ゴールイメージ全体（§1.1〜§1.8）に大きな抜けや誤認はないか**
2. **シナリオA/B/Cの想定**（一般ユーザーは差分指示中心、新規生成は上級向け）に同意できるか
3. **決定論性をエンジン側責務とする**方針に同意できるか
4. **パラメータオーバーライドモデル**は A+C ハイブリッドで進めてよいか、別案を検討すべきか
5. **スプライト余白は自動算出 + UI オーバーライド** という二段構えでよいか
6. **Option γ（コアのみ流用・他は再設計）でよいか**、それとも Option β に留めるか、δ まで踏み込むか
7. **Phase 0 として「暗黙知抽出」を独立フェーズに置く合意**
8. **次の一手**:
   - (a) 方針確定 → 「Phase 0 計画」を新規作成して既存実装の暗黙知抽出から着手
   - (b) 方針確定 → 同時並行で「IR 設計詳細プラン」を新規作成
   - (c) PoC を優先（既存テンプレ1本を Atom 分解→IR JSON→Compiler 試作で通すまでの最短ルート）
